あなたのリポジトリで公表されている帰属の記述に異議を申し立てるために、この書簡を書いています。その記述は、ページで言及されているカートリッジを、あなたによるS-DD1を使用しないStreet Fighter Alpha 2の実装を商品化したものとしています。

この版の出所について、私は明確に表明します。私の解凍処理と、29LV640メモリ向けに用意したパッチを通じて提供した、Shin Akumaと読み込み高速化を備えた8 MiBのUSA版に、あなたのプロジェクトの素材は利用していません。私がここで言及しているカートリッジは、この版を使用していると表明します。実際に使用されている内容を技術的に特定することなく、これらのカートリッジをあなたのプロジェクトに帰属させることに異議を申し立てます。

この書簡の目的は、問題となっている版の出所を明らかにし、私の取り組みの経緯を説明するとともに、公に示す帰属を検証可能な証拠で裏付けるよう求めることです。

## 1. 私のプロジェクトの歩み

私の取り組みは、8 MiB用パッチの提供から始まったわけではありません。それ以前に、S-DD1の研究、ツールの開発、マッピングの分析、基板の組み立て、修正、そしてSNES実機でのテストという過程がありました。

当初の計画は、データへのアクセスを制御し、実装の詳細を保護するためのCPLDを搭載したPCBを使用するものでした。解凍、データの配置、再構築に関わるこの仕組み全体を一般公開するつもりはありませんでした。

あなたのプロジェクトの公開を知ったとき、私は意欲を大きく失いました。それまで時間と労力を注いできた取り組みの独自性が損なわれたと考えるようになりました。これが、当時の私のプロジェクトの将来に対する受け止め方でした。

そうした状況の中で、すでに行った取り組みを継続するために方針を転換し、8 MiB版の解凍処理とパッチを非公開で提供することにしました。この判断は、私が提供した版を自動的にあなたのリポジトリの一つのバージョンとみなす根拠にはなりません。

## 2. 私の解凍手法の仕組み

sdd1_unpackerの元のコアでは、bsnesに存在するS-DD1の実装を研究し、切り出しました。コードのクレジットは維持しました。元のアルゴリズムおよび実装についてはAndreas Naive、bsnesへの移植についてはbyuuです。私はS-DD1アルゴリズムを発明したとは主張していません。

このコードを、グラフィカルインターフェースやエミュレータ全体の動作に依存しないC++ツールに適応させ、ROMデータの検証を伴う読み取りと、S-DD1のメモリバンクの処理に対応させました。

ゲームはROM全体を一つの圧縮ファイルとして扱っているわけではありません。通常はDMA転送の際に、個別のストリームを要求します。そのため、この作業には、元のROMのディスクリプタとテーブルの分析、実行中に行われたリクエストの記録、そして取得元、サイズ、メモリバンクの設定をまとめることが含まれていました。

過去の再構築における正規のトレースには、3,160行に3,155件のリクエスト識別情報があります。追加の五行は、すでにカタログ化されたリクエストについて、別の呼び出し箇所からの証拠を記録したものです。実際に観測されたリクエストと静的に推定したエントリは、別々に分類しています。この数値は、3,155種類の異なる圧縮ストリームを意味するものではなく、それだけでゲーム内のあらゆる状況を網羅していると証明するものでもありません。

元のコアの処理の流れは、元のUSA版ROM、分析とトレース、リクエストのカタログ、データの解凍、新しいレイアウトへの配置、DMAパッチ、そしてS-DD1を使用しない再構築の検証、という構成でした。

この再構築では、CPUアドレスとファイル内のオフセットを区別し、SNESのROM領域に従い、対象となるルーチンの参照先を解凍済みデータに変更する必要がありました。単にファイルを大きくしたり、ヘッダーを変更したりするだけのものではありません。

## 3. 8 MiBへの適応とシンプルな基板

8 MiBの系統は、それ以前の16 MiBの再構築コアと区別する必要があります。この系統では、私がテストを行い、YouTubeに投稿した16mbのベースから抽出したインベントリを使用し、その後の修正と検証も加えて、別のデータ整理と割り当ての工程を経ています。16 MiBのファイルから単純に切り出したものとして説明しているわけではありません。

この版は、適切な配線と、x8モードの29LV640という単一の8 MiB TSOP48フラッシュメモリを用いた、シンプルな基板向けに用意したものです。この構成で動作するためにS-DD1やCPLDは必要なく、SNES実機でテストしました。改造したLoROM基板向けの派生版も用意しました。

あなたのプロジェクトに記載されている、過去の12 MiBへの変換とは、客観的な違いがあります。その12 MiBのイメージを、8 MiBの29LV640にそのまま書き込み、私が実演した構成で使用することはできません。あなた自身の技術的な説明には、C0-FFバンクのウィンドウを含む、固有のマッピングが記されています。

https://github.com/snes9xgit/snes9x/issues/1081

あなたの実装を物理的なカートリッジ向けに適応させることが決してできないと主張しているわけではなく、あなたが記録したハードウェア上のテストを否定しているわけでもありません。12 MiBのイメージとそのマッピングを、私の基板構成向けに用意した8 MiB版と区別しているのです。

ゲームを利用できる人を増やすことが目的ならば、この方法も認めることが重要だと考えます。つまり、特定のフラッシュカートを購入する必要なく、シンプルな基板と入手しやすい部品を使えるようにすることです。この取り組みで使用したテスト基板は、すでに記録していました。その動画は、この書簡の末尾の一覧に含まれています。
